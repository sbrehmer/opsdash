# Research: Core Dashboard Host

Phase 0 output for [plan.md](./plan.md). Every Technical Context unknown is resolved below.
The dependency rules come from Constitution Principle IV: prefer an established library over
hand-written boilerplate, and justify each runtime dependency.

## R1. Language and runtime

- **Decision**: TypeScript 5.x (strict) on Node.js 24 LTS for the server, and the same
  TypeScript for the web client and plugins.
- **Rationale**: The user chose TypeScript full-stack. With one language, a plugin's server
  part and widget can share types. Node 24 can run erasable TypeScript directly (built-in
  type stripping) and has `node --watch`, `util.parseEnv`, and `AbortSignal.timeout`. That
  removes the need for a transpiler, `dotenv`, or a watcher dependency for the server.
- **Alternatives considered**: Python with HTMX (the recommended option, which the user
  declined); Go with templ (plugins would have to be compiled in); Bun or Deno (smaller
  ecosystem for `better-sqlite3` and Drizzle tooling).
- **Consequence**: `tsconfig` sets `erasableSyntaxOnly` and `verbatimModuleSyntax`, which
  rules out `enum` and parameter properties. Imports use explicit `.ts` extensions
  (`allowImportingTsExtensions` with `noEmit` for the server). A type check (`tsc --noEmit`)
  runs in CI.

## R2. HTTP server and push channel

- **Decision**: Hono on `@hono/node-server`, with Hono's `streamSSE` for server-sent events.
- **Rationale**: Hono is small and TypeScript-first, with built-in SSE, static file serving,
  and request validation middleware. SSE is one-way server→browser, which is all FR-022
  needs. It works through proxies and reconnects automatically through the browser's
  `EventSource`.
- **Alternatives considered**: Fastify (heavier plugin system that isn't needed); Express
  (untyped, slower); WebSockets (two-way, which isn't needed, and needs an extra library and
  reconnect logic).

## R3. Frontend

- **Decision**: Vite 8 (current major at implementation time; the plan said 7) + Preact 10 +
  `@preact/signals`. Plain CSS using custom properties
  (design tokens) and CSS Grid. No component or CSS framework.
- **Rationale**: The user fixed Vite and Preact. Preact is about 4 KB gzipped, which fits
  "lightweight". Signals give fine-grained updates when SSE pushes data for single widgets.
  A 12-column CSS Grid maps directly onto FR-002b, and tokens as CSS custom properties map
  onto FR-037.
- **Alternatives considered**: Tailwind (conflicts with the rule against plugin global
  styles and adds build complexity); a component library (heavier than the minimalist UI
  needs).

## R4. Loading plugin widgets without rebuilding the host

- **Decision**: Each plugin ships a prebuilt ES module client bundle (`dist/client.js`) that
  treats `preact`, `preact/hooks`, `@preact/signals`, and `@opsdash/plugin-sdk/client` as
  externals. The host page declares an **import map** that points those specifiers to the
  host's own copies. The host serves each plugin's bundle at `/plugins/<id>/client.js` and
  loads it with dynamic `import()`. The SDK ships a Vite library-mode preset
  (`@opsdash/plugin-sdk/vite`) that sets up these externals.
- **Implementation note**: the import map points to `/vendor/*.js` shims generated by the host.
  They re-export the module instances the page itself uses (published on
  `globalThis.__opsdash_shared` by the web entry). This gives one shared Preact instance in
  production and under the Vite dev server with HMR. `@opsdash/plugin-sdk/client` is stateless
  and bundled into each plugin instead of being shared. Mapping to Vite's hashed dependency URLs
  was rejected because it breaks in dev.
- **Rationale**: Plugins can be dropped into the plugin directory without rebuilding the
  host (FR-014, US8), and every widget shares one Preact instance so hooks and context
  work. Import maps are supported in every evergreen browser.
- **Alternatives considered**: Module Federation (heavy, and tied to the bundler); iframes
  (isolated but awkward for theming, and costly with many widgets); Web Components per
  plugin (would still need a shared framework or duplicated runtimes).

## R5. Configuration parsing with line and column errors

- **Decision**: The `yaml` package (eemeli/yaml) with `LineCounter`, parsing to a `Document`
  so that each node keeps its source range. Validation uses **Zod 4**, and each Zod issue
  path is mapped back to a node range, which gives file + line:column + document path
  (FR-008). The published schema is generated with `z.toJSONSchema()` (FR-013), so editors
  can autocomplete through `yaml-language-server`.
- **Rationale**: `yaml` is the most complete YAML 1.2 parser for JavaScript and keeps
  positions. Zod 4 gives typed parsing, clear issues, and JSON Schema output from one
  definition, so there's no second schema to maintain.
- **Alternatives considered**: `js-yaml` (no positions kept on nodes); Ajv with a
  hand-written JSON Schema (two sources of truth for types); Valibot (smaller, but weaker
  JSON Schema export).
- **Includes**: A top-level `include:` list of relative paths, resolved against the including
  file. There's no custom YAML tag, so standard editors and linters stay happy. Include
  cycles are found with a DFS visited-set.

## R6. Watching files and hot reload

- **Decision**: `chokidar` 4 watches the config directory, the env file, and the plugin
  directory, with a debounce of about 150 ms.
- **Rationale**: Editors write files atomically (rename-swap), and chokidar handles that
  more reliably than raw `fs.watch`. It is small (v4 has one dependency) and widely used.
- **Dev hot reload** (user request):
  - **Web**: Vite dev server with HMR for the host UI. It proxies `/api` and `/plugins` to
    the host server.
  - **Host server**: `node --watch` restarts the server when a source file changes. No
    extra dependency.
  - **Plugins**: in dev, each plugin in the workspace runs `vite build --watch`. The host's
    plugin watcher sees `dist/` change, re-imports the server module with a cache-busting
    query, re-validates the manifest, and sends a `plugin-reloaded` SSE event. The browser
    then re-imports that plugin's client module and re-mounts only its widgets.
  - **Config**: this is a product feature (FR-011), not just a dev tool. It uses the same
    watcher.
  - `pnpm dev` starts all of these together (Vite, `node --watch`, and plugin watch builds)
    through pnpm's parallel recursive run, with no process-manager dependency.

## R7. Storage layer

- **Decision**: **Drizzle ORM** with the `better-sqlite3` driver, and **drizzle-kit** for
  generating migrations. Migrations run at startup through
  `drizzle-orm/better-sqlite3/migrator`.
- **Rationale**: Drizzle is TypeScript-first and supports SQLite, PostgreSQL, and MySQL with
  a near-identical schema API. That satisfies the constitution's requirement for a
  multi-dialect ORM without us building an abstraction. `better-sqlite3` is the most mature
  synchronous SQLite driver for Node. drizzle-kit produces versioned SQL migrations that can
  be checked into the repo.
- **Alternatives considered**: Kysely (a query builder with separate migration tooling);
  Prisma (heavy engine binary, which conflicts with "lightweight"); `node:sqlite` (still
  flagged experimental in parts, and Drizzle support is less mature).
- **Refusing incompatible stores (FR-031)**: before migrating, the host compares the
  store's applied migration journal with the ones bundled with the host. If the store has
  migrations the host doesn't know about, the store is newer, so the host refuses to start
  and leaves the file untouched. `PRAGMA integrity_check` runs at startup, and a failure
  also refuses to start.
- **Settings**: WAL journal mode and `foreign_keys = ON`, so that cascade deletes on links
  work.
- **Implementation note**: `packages/host/src/store/drizzle.ts` loads drizzle-orm's CommonJS
  build. On Node 24 its ESM build measured about 260 MB RSS and 0.6 s to load, against about
  66 MB and 0.1 s for CommonJS, which broke the idle-memory budget (R14). Idle RSS dropped from
  237 MB to 124 MB.

## R8. Secrets

- **Decision**: The env file is read with Node's built-in `util.parseEnv`. Its values fill
  only keys that are missing from `process.env`, so the process environment wins (FR-033).
  Secret-typed settings use an SDK helper, `secret()`, which accepts only `{ env: "NAME" }`
  and rejects literal strings with a message pointing to FR-034. The values are handed only
  to server-side plugin code through `ctx.secrets.get(name)`, and only for names the
  manifest declares.
- **Redaction**: pino's `redact` handles known key paths. A small hook also replaces any
  currently loaded secret value found in log messages or error strings with `[REDACTED]`.
  This needs a little custom code (about 20 lines), because no library redacts by value.
- **Alternatives considered**: `dotenv` (not needed on Node 24).

## R9. Logging and health

- **Decision**: **pino** writes structured JSON logs to stdout (FR-046). `GET /healthz`
  returns `{status: "healthy"|"degraded"|"unhealthy", reasons: [...]}`, with HTTP 200 for
  healthy or degraded and 503 for unhealthy (FR-047).
- **Rationale**: pino is the de facto standard for fast structured logging in Node.
  Degraded still returns 200, so a proxy doesn't take the whole dashboard down over one bad
  plugin.

## R10. Refresh cycle, batching, and cache

- **Decision**: One **scheduler** runs in the host process:
  - **Visible set**: the union of the widget paths on every dashboard that currently has at
    least one open SSE subscriber.
  - **Timing**: one timer per plugin, at the plugin's effective interval (config override,
    then manifest default, then the global default of 60 s). There's an in-flight flag per
    plugin, so a tick that's due while the previous one is still running is skipped
    (FR-026).
  - **Per tick**:
    1. Collect the references needed by the visible widgets of that plugin.
    2. Remove duplicates by `refKey`.
    3. Drop references still inside the cache window.
    4. Group by the plugin's optional `batchKey(settings)`. By default everything falls in
       one group.
    5. Split each group into chunks of at most `maxBatchSize`.
    6. Call `plugin.fetch()` once per chunk, with `AbortSignal.timeout(plugin.timeout)`.
    7. Map the results back to widgets and push them over SSE.
  - **Opening a dashboard** (FR-022): the viewer's widgets that are already covered get the
    last results immediately. Widgets that weren't covered yet get an immediate out-of-cycle
    fetch, run through the same pipeline.
  - **Cache**: `lru-cache` with a TTL equal to the cache window (default 30 s). It's keyed
    by `pluginId|batchKey|refKey`.
- **Rate limiting**: the constitution lists rate limiting among the host data-access helpers
  "where those exist". None is built in this feature. The reference source has no rate
  limit, and the cache and batching already cap request volume. A per-plugin rate limiter
  is deferred to the first source-system plugin whose source enforces limits.
- **Rationale**: This meets FR-022 to FR-027 and SC-003/004. Grouping by `batchKey` is
  needed when widgets of the same plugin point at different source instances (for example
  two base URLs). The spec's "one batched fetch per plugin" becomes "one per plugin per
  distinct source". It's documented in the contract.
- **Alternatives considered**: A job-queue library (over-engineered for one process); a
  hand-written TTL map (`lru-cache` is already standard and bounds memory).

## R11. Mock mode (user request)

- **Decision**: Mock mode is switched on by `--mock` or `OPSDASH_MOCK=1` (FR-048). Every
  plugin **must** export a `mock` source that has the same `fetch` and `parseReference`
  signatures as its real source (FR-049). In mock mode:
  - the host calls `mock.fetch` in place of `fetch`;
  - secrets are not resolved, and missing environment variables are not errors;
  - the UI shows a persistent "Mock mode" badge (FR-050).
- The SDK provides `createMockSource({ generate, faults })`. `generate(ref)` returns
  deterministic, seeded, realistic data. `faults` is controlled by the plugin's settings or
  a `mock` config section (for example `notFound: ["X-404"]`, `errorRate`, `latencyMs`,
  `partialFailure`). Contract and E2E tests run the reference plugin in mock mode.
- **Rationale**: Developers, demos, and CI can run without any source systems or
  credentials. Because the scheduler, batching, and cache paths are identical in both
  modes, SC-003 can be measured in mock mode.
- **Alternatives considered**: HTTP-level mocking such as MSW or nock (tied to each
  plugin's transport, and wouldn't prove batching at the plugin boundary); letting each
  plugin choose freely (inconsistent developer experience).

## R12. Testing

- **Decision**:
  - **Vitest** for unit, integration, and contract tests: config loader and error
    locations, scheduler batching and de-duplication, storage and migrations, secrets and
    redaction, and plugin contract tests.
  - **Playwright** for end-to-end tests against the built app in mock mode: rendering,
    themes, tracking flow, isolation, and hot reload of config. `@axe-core/playwright`
    checks WCAG 2.2 AA (SC-010) at the 360, 1280, and 3840 px viewports.
- **Implementation notes**: Vitest 5 uses `test.projects` in `vitest.config.ts`
  (`vitest.workspace.ts` is gone). The devcontainer is Alpine (musl), where Playwright's
  bundled Chromium can't run, so E2E uses a system Chromium through `OPSDASH_CHROMIUM`. CI on
  Ubuntu uses the bundled browser.
- **Rationale**: Vitest shares Vite's config and understands TypeScript natively.
  Playwright plus axe is the standard way to test accessibility automatically.

## R13. Monorepo and packaging

- **Decision**: A pnpm workspace with four packages: `packages/host` (server),
  `packages/web` (Vite and Preact UI), `packages/plugin-sdk` (types, Zod re-export,
  `secret()`, the mock helper, and the Vite preset), and `plugins/reference`. Opsdash ships
  as one Node process: `opsdash --config <dir> --plugins <dir> --db <file>
  [--env-file <file>] [--mock]`. It serves the API, SSE, the built web assets, and plugin
  bundles on one port.
- **Rationale**: The SDK has to be a separate package that plugin authors can depend on. The
  reference plugin lives in its own package so it proves it uses only the public API (FR-020).
  Everything is still a single deployable.
- **Deferred**: a container image, to be added when a deployment target needs it (YAGNI).

## R14. Size and startup budget (constitution requirement)

- **Decision**: These limits are enforced in CI from now on.
  - **Host web bundle**: 60 KB gzipped at most for the initial JavaScript, and 15 KB
    gzipped at most for CSS. Checked with `size-limit`.
  - **Reference plugin client bundle**: 10 KB gzipped at most.
  - **Server cold start** to `/healthz` healthy: 1.5 s at most, with the reference plugin
    and an empty store, on CI hardware.
  - **Server RSS at idle**: 150 MB at most.
